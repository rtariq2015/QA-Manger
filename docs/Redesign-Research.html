RESEARCH & DESIGN PROPOSAL · 10 NOVEMBER 2026

Make the whole program simple.

Open it. See what needs attention. Approve or disapprove pending files. Find or export reports. Keep the technical work in the background.

This document records the research before implementation. It is not a new program or a working prototype. The installed v4.4.1 application is unchanged.

The recommended experience

TodayDaily report receipt, monthly evidence progress, and the last successful update.
ReportsFind PDFs, review pending suggestions, open folders, and export a report package.
SettingsConnections, archive location, updates, backups, and support logs.
Open program→See new reports→Approve / Disapprove→Done

The proposed interface uses local HTML, CSS and JavaScript. A local Windows helper handles folders, scanner access and saved data. Core work stays offline. The host technology remains conditional on a compatibility check; changing to HTML alone does not guarantee speed or successful scanner connections.

Pending file review: exactly two main actions

ApproveDisapprove
  • Approve: keep the suggested report type, save the decision, remove it from pending and display the next PDF.
  • Disapprove: reject the suggested type, keep the PDF under Other reports, clear it from pending and display the next PDF.
  • Undo: a secondary action restores the previous classification and pending state, while retaining the decision history.
  • Moving to another file or leaving the screen without deciding leaves that report pending. Changing an already sorted type remains available in report details.

No name field, authorization checkbox, typed reason or second confirmation for routine file sorting. The activity record saves the time, action and available Windows account identifier automatically. A shared Windows account is recorded as an account, not represented as a verified individual reviewer.

The preview and two action buttons stay visible together. Only genuinely ambiguous report types enter this queue; clearly recognized document types can be organized automatically. A previously disapproved suggestion must stay resolved when the same source bytes are imported again.

These buttons approve or reject the suggested file classification. They do not record a clinical PASS/FAIL or silently complete a Monthly QA checklist. The interface should explain that once in plain language, without putting another approval form in the daily flow.

If the department uses formal named QA sign-off, keep it in the monthly evidence workspace as a separate function. Existing reviewer names and evidence remain intact. Opening a preview is logged as opening a preview, not as proof that every page was inspected.

This is an illustrative local-workspace layout, not real scanner data. An existing archive on another configured local drive remains supported; migration must not silently move it.

There is one Monthly folder per scanner/month. Pending and approved are app statuses, not extra folder layers. Approving a suggested Monthly report therefore does not shuffle it between Pending and Confirmed folders. Actually changing a report's type can update its readable location through a verified transfer.

A combined Monthly PDF and several component PDFs both fit naturally. Preserve original names in the details and export inventory; use a readable suffix for legitimate separate sessions and revisions. Keep undated reports explicit instead of inventing a date.

One visible library does not mean removing protected copies. Initially retain the verified archive and past revisions in the internal data area. This preserves recovery when someone edits, renames or drags a readable PDF. Reducing physical duplicate storage is a separate later decision. Same-drive copies are not a substitute for a backup on approved separate storage.

Keep normal work short

SituationProposed behavior
First openingLocate the existing workspace before offering a new empty archive. Show its location, report count and date range.
Scanner setupLoad the local connection profile, test one scanner, and explain the exact connection result. A saved password is not displayed as a successful connection.
Daily importsCopy and analyze new or changed PDFs. Reuse cached results. Let the user browse saved reports while imports run.
Monthly viewGroup by scanner and month. Show received PDFs and explicitly verified checklist items separately. Several PDFs may contribute to the same checklist.
Historical archive findingsGroup informational items in Settings → Storage health. Show only relevant, actionable summaries on Today; a missing archived PDF is not described as a clinical failure.
Sharing reportsChoose scanner and period, then Export. Produce readable filenames, PDFs and an offline summary.
UpdatingChoose one update ZIP in Settings. Preserve the workspace, connections, saved history and previous-program rollback copy.
Getting supportOne Export support logs action. Show safe status, timing and Windows error numbers without sharing passwords or report contents.

Display meaningful text rather than color alone, label controls clearly and keep keyboard focus and primary actions visible at smaller window sizes. These choices follow W3C guidance on identifying errors and visible keyboard focus.

Offline first, optional internet later

Bundle the interface, styles, icons, PDF support and necessary helper components with the program. Normal use needs no public website, account login, external fonts, CDN or internet connection. The internal hospital network is still needed to collect new scanner reports; saved reports remain usable when scanners are unavailable.

Optional update notices and reference material can be separate, disabled-by-default features. A blocked online destination must not block local work. Cross-workstation shared records require a separately designed, approved server and concurrency model. Cloud AI is not part of the core redesign, and no reports or logs are uploaded automatically.

Keep durable reports, decisions and configuration in the workspace, not solely in browser storage. Moving the workspace should retain its records. Windows-encrypted scanner sign-ins may need re-entry on another computer or account.

Research evidence and implementation decisions

What the current source shows

Baseline inspected: v4.4.1, commit 815a163c5947eba09d6c2d1584745065fbaa6664. These are code findings, not newly executed compatibility tests.

  • ReviewQueueUi.ps1:4 requires preview state, name and authorization before enabling a decision. Archive.psm1:752 also requires reviewer and reason. Removing fields only from the new screen would not fix that coupling.
  • Review.psm1:39–60 and Archive.psm1:622 reuse named confirmation fields in pending and Monthly evidence logic. Introduce separate document-classification decisions, activity actors and evidence verification. Do not silently fill clinical reviewer fields with the Windows username.
  • Archive.psm1:305 uses category and identity paths. Browse.psm1:78 creates a second readable tree and ledger. Simplify the exposed library while retaining verification and recovery.
  • Start.ps1:760 and its completion dispatcher mix view state, scheduling and operation results. Extract a small host/service interface over the existing modules; do not rewrite functioning preservation logic merely to change the screen.
  • Keep the existing SHA-256 verification, stale-decision checks, reversible history, protected credentials, bounded worker operations, writer locks, revision preservation and offline ZIP updater. Preserve the explicit union of checklist evidence across multiple PDFs.

What primary documentation establishes

EvidenceConsequence for this program
MDN File System APIBrowser access to visible files and directories is permission-based. A single HTML file cannot transparently replace Windows scanner authentication and background folder collection.
MDN localStorageStorage is tied to browser origins, and behavior for file URLs is undefined. Use the portable workspace as the authoritative store.
Microsoft WebView2 distributionProduction WebView2 needs its runtime; having normal Edge installed is insufficient. Use it only if the required runtime already exists and is permitted. Do not auto-install a missing runtime.
Microsoft HttpListener and URL reservationsMicrosoft discourages new HttpListener development. Windows HTTP.sys namespace rights can involve URL reservations. Do not make administrative URL ACL changes part of normal setup.
Microsoft Edge local network accessCurrent guidance distinguishes public-site requests from local-to-local requests. It does not establish that this workstation permits a local helper. Prefer serving the interface and API together locally, rather than having an internet site control local files.

Architecture recommendation, still conditional

First evaluate installed Edge with a maintained, packaged local host using the existing archive/network modules. A bundled host can avoid runtime installation, but adds program components and still has to pass endpoint policy. Do not create a bespoke production HTTP parser to avoid deployment questions. If an already available WebView2 runtime offers better permitted operation, evaluate that alternative. Keep the WPF version usable during this decision.

The helper should accept narrow actions by report ID: list reports, preview PDF, approve suggestion, disapprove suggestion, undo decision, list job status and export reports. It must not expose arbitrary shell commands or unrestricted file paths. Serve on loopback only with request authentication and same-origin controls; do not expose it on the hospital LAN. Keep remote content away from privileged controls.

Move job scheduling out of the screen. Use saved read snapshots so importing does not freeze the library; serialize changes to the archive. Cache extracted text and preview data using the report fingerprint. Measure startup, next-PDF latency, import throughput and memory with representative synthetic archives before calling the redesign faster.

Order of work

  1. Research and workflow specification — completed in this document. Use the requested two-button file review and three main areas.
  2. Compatibility proof. Verify that the selected HTML host launches without administrator rights, installs or machine configuration changes. Exercise one synthetic PDF, one reversible classification, restart persistence, safe shutdown and the existing interface fallback. Check one scanner connection separately on the actual work computer.
  3. Build the simple daily flow. Today, Reports with Approve/Disapprove, readable folders, and Settings. Keep the two-button decision independent of clinical checklist verification.
  4. Migrate a copy of an existing archive. Preserve IDs, hashes, scanner aliases, original filenames, reviewer/evidence history and checklist history. Build the new readable tree separately, verify hashes and counts, compare statuses and coverage, then switch only after validation. Keep the previous archive intact for rollback. Never modify scanner originals.
  5. Validate the complete workflow. Include real keyboard input paths, clicks, small-screen layouts, unavailable scanners, changed files, failed saves, unchanged rescans, Undo after restart, multiple Monthly component PDFs, moves and updates. Ordinary Approve/Disapprove must never invent a reviewer or clinical result.
  6. Add optional online features afterward. Test blocked and disconnected operation as normal cases, with no automatic report upload.
